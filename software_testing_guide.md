I. Objectives
This document provides comprehensive guidance for the automated generation and management of test cases using an AI tool integrated with Jira and Git. The main goal is to ensure software quality by creating comprehensive, accurate, non-duplicate, and easy-to-understand test cases, optimizing the testing process, and enhancing development efficiency.
II. Automated Test Case Generation Process
The AI tool will generate test cases based on information from Jira tickets and Git source code. The general process is as follows:
Jira Ticket Analysis: The AI will read and analyze descriptions, requirements, Acceptance Criteria (AC), and other information fields in Jira tickets to understand the feature to be tested. This is the primary source of information for test case generation. The AI will use requirement analysis techniques from Section VIII.1 to ensure a clear and deep understanding of this information.
Git Source Code Analysis (if applicable): For cases requiring detailed testing of implementation or enriching information for special scenarios, the AI can analyze related source code to better understand the logic and potential scenarios. However, the AI will not rely on Git diff to generate basic test cases, but only use it to supplement context and support techniques like White Box Testing (Section VIII.2.B) when needed.
Integration of Existing Test Cases: The AI will prioritize test cases already attached or linked in existing Jira tickets. This simultaneously adheres to the Non-duplicate principle (Section V) and utilizes test case management strategies from Section X.2 (Test Case Reuse).
New Test Case Generation: Based on the analysis, the AI will generate new test cases to ensure maximum coverage for requirements. This process will extensively use the types of Test Case scenarios to focus on (Section IV) and apply Test Case design techniques (Section VIII.2) such as Equivalence Partitioning, Boundary Value Analysis, Decision Table Testing, etc., while combining with Error Guessing and Risk-Based Testing (Section VIII.3).
Duplicate Check: The AI will compare newly generated test cases with existing test cases to avoid duplication, ensuring compliance with the Requirements for Generated Test Cases (Section V).
Formatting and Export: The generated test cases will strictly follow the Test Case Generation Formatting Guidelines (Section III) and the Structure and Content of an Effective Test Case (Section IX), including SMART principles for Expected Results and other best practices. The test cases will be exported to the corresponding file.
III. Test Case Generation Formatting Guidelines (For AI)
To ensure consistency and high readability, all test cases generated by the AI must adhere to the following format:
Example:
TC1: [{service_name}] Verify API login returns status_code = 200 and response ="Login successful", Case with valid parameters username = testuser, password =password123
TC2: [{service_name}] Verify API login returns status_code = 400 and response ="Invalid credentials", Case with valid username = testuser, invalid password =wrongpassword
Each Test Case must provide the following complete information:
Test Case Key: TCx (e.g., TC1, TC2, TC3...). This is the unique identifier for each test case.
Test Case Name:
Starts with [{service_name}] to indicate the service or module being tested (e.g., [Auth Service], [User Profile API]).
Briefly and concisely describes the behavior to be tested.
Clearly states the expected result of the test (e.g., returns status_code = 200 and response ="Login successful").
Test Scenario Description: Details the test scenario, including specific input conditions and context (e.g., Case with valid parameters username = testuser, password =password123).
Request Parameters/Body (Optional): Lists the parameters or body of the request (e.g., username = testuser, password =password123).
Required scenario types:
Happy path scenarios
Error scenarios
Boundary conditions
Edge cases
Different HTTP methods if applicable
Various parameter combinations
V. Requirements for Generated Test Cases
The test cases generated by AI must meet the following criteria:
Comprehensive: Cover all possible scenarios based on requirements and analysis, combining test types from Section VII.2.
Non-duplicate: No test cases duplicate in purpose or scenario with existing test cases. The AI will use test case management mechanisms from Section X.2 (Test Case Reuse and Test Suite Maintenance).
Clear and Descriptive: Easy to understand, providing enough information to execute and verify, adhering to principles from Section IX.3 (Writing Clear, Concise, Easy-to-Understand Test Cases).
Following the specified format: Ensure correct structure and defined components according to Section III and Section IX.1 (Mandatory Fields of a Test Case).

Acceptance Criteria: Acceptance criteria.
Analysis techniques (for AI and Tester):

Identify "if-then" conditions.

Identify special cases.
B. Questioning techniques to clarify requirements:

Test Case Design Techniques
A. BLACK BOX TESTING:
The AI will primarily use Black Box Testing techniques based on requirements and input/output parameters to ensure functional coverage.
EQUIVALENCE PARTITIONING:
Divides input into equivalent groups.
Each group has the same processing behavior.
Select 1 representative value for each group.
Example: User age (0-17, 18-65, 66+).
BOUNDARY VALUE ANALYSIS:
Tests values at and near boundaries.
Includes: min, min-1, min+1, max, max-1, max+1.
Example: Age from 18-65, test with 17, 18, 19, 64, 65, 66.
DECISION TABLE TESTING:
Lists all conditions and results.
Creates test cases for each combination of conditions.
Example: Decision table for login function (Username Valid/Invalid, Password Valid/Invalid).
STATE TRANSITION TESTING:
Tests system state transitions.
Identifies current state, event, new state.
Example: Order status (Draft → Pending → Approved → Shipped → Delivered).
USE CASE TESTING:
Writes test cases based on Use Cases.
Tests main flows and alternative flows.
Tests exception flows.
B. WHITE BOX TESTING (Basic Introduction):
Although AI does not directly perform White Box Testing like humans, understanding these concepts helps AI (if integrated with code analysis capabilities) to generate smarter test cases and explain the rationale for certain test cases, especially when information from Git diff is available.
STATEMENT COVERAGE:
Ensures each statement is executed at least once.
Lowest coverage level, easy to achieve.
BRANCH COVERAGE:
Ensures each branch (if-else) is executed.
Includes both true and false branches.
PATH COVERAGE:
Ensures every possible path is executed.
Highest coverage level, difficult to achieve.
Why Testers should understand White Box Testing (and AI can also benefit from this knowledge):
Understand code logic to design better test cases.
Know which parts of the code need more testing.
Can discuss test coverage with developers.
C. EXPLORATORY TESTING:
This technique is primarily for humans, but AI can learn from Exploratory Testing data patterns to improve its ability to generate test cases for unpredictable scenarios. AI can analyze data from defect reports or exploratory testing notes to identify similar scenarios in the future.
When to use: When requirements are unclear, short time.
How to perform effectively:
Prepare a basic checklist.
Document what has been tested.
Focus on main functions.
Try unusual cases.

A. ERROR GUESSING:
Based on experience to predict common defects.

B. CHECKLIST-BASED TESTING:

C. RISK-BASED TESTING:
AI can analyze information from Jira (ticket priority, component, etc.) and Git (code complexity, recent change frequency) to assess risk and prioritize test case generation, focusing on critical and error-prone areas.
How to prioritize testing based on risk:
High impact + High likelihood = Highest priority.
High impact + Low likelihood = High priority.
Low impact + High likelihood = Medium priority.
Low impact + Low likelihood = Low priority.
Risk assessment factors (AI needs to consider):
Impact on users.
Impact on business.
Frequency of function usage.
Code complexity.
Module defect history.

IX. Structure and Content of an Effective Test Case
This is the standard for AI to ensure generated test cases are high-quality and easy for users to understand.
Mandatory Fields of a Test Case
Although AI generates in its own format (Section III), it needs to "understand" these components to ensure test cases have complete information.
TEST CASE ID:
Unique identifier.
Format: TC_001, TC_002, or TC_FUNC_001.
Easy to reference and track.
TITLE (Test Case Name):
Briefly describes the test purpose.
Example: "Verify successful login with valid credentials".
Not too long, not too short.
DESCRIPTION:
Detailed explanation of the test case.
Purpose and scope of the test.
Conditions and assumptions.
PRE-CONDITIONS:
Conditions necessary before performing the test.
Example: User has registered an account, system is operating normally.
Necessary data has been prepared.
TEST STEPS:
Lists specific, clear steps.
Numbered: 1, 2, 3...
Each step performs only one action.
Includes specific input data.
EXPECTED RESULT:
Precisely describes the expected outcome.
Adheres to SMART principles (Section IX.2).
Measurable and verifiable.
ACTUAL RESULT:
Records the actual result when performing the test.
Compares with Expected Result.
Notes if there is a difference.
STATUS:
Pass: Test case successful.
Fail: Test case failed.
Blocked: Test case blocked.
Not Executed: Not yet executed.
SMART Principles for Writing Expected Results
The AI needs to strictly apply this principle to ensure expected results are clear and verifiable.
SPECIFIC:
Precisely describes the expected outcome.
Avoids vague terms like "functions normally".
Example: "Displays 'Login successful' message".
MEASURABLE:
Results can be tested and confirmed.
Observable or measurable.
Example: "Returns status code 200".
ACHIEVABLE:
Realistic and feasible results.
Consistent with system capabilities.
Example: "Response time < 3 seconds".
RELEVANT:
Results are relevant to the test purpose.
Meets business requirements.
Example: "Data is saved to the database".
TIME-BOUND:
Specifies expected response time.
Example: "Returns results within 5 seconds".
Writing Clear, Concise, Easy-to-Understand Test Cases
The AI will prioritize clarity and readability in all generated test cases.
Writing principles:
Use simple, easy-to-understand language.
Avoid complex technical jargon.
Each step performs only one action.
Use imperative verbs: "Enter", "Click", "Verify".
Clear structure:
Name test case to clearly describe its purpose.
Arrange steps in logical order.
Use bullet points or numbering.
Clearly separate sections.
Easy to reproduce:
Provide all necessary information.
Include specific test data.
Describe the test environment.
Note special conditions.
How to Write Negative Test Cases
The AI will focus on error scenarios to assess system robustness.
Purpose:
Test the system's error handling capability.
Ensure the system does not crash with invalid input.
Verify appropriate error messages.
Types of Negative Test Cases (AI needs to consider):
Invalid input.
Empty input.
Oversized input.
Wrong format input.
Non-existent data.
Examples of Negative Test Cases:
Login with non-existent username.
Register with invalid email format.
Search with empty keyword.
Upload oversized file.
Enter negative age.
How to Write Edge Cases
The AI will look for boundary values and special cases to detect subtle defects.
Definition:
Test cases that test values at boundaries.
Tests limiting cases.
Detects logical errors at transition points.
Types of Edge Cases (AI needs to consider):
Minimum value.
Maximum value.
Null/empty value.
Special characters.
Zero value.
Examples of Edge Cases:
Username with minimum length (1 character).
Username with maximum length (50 characters).
Password containing only spaces.
Email containing only special characters.
Age = 0 or age = 150.
